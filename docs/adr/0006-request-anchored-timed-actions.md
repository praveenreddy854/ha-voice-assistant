# Request-anchored deadlines and durable timed action phases

Relative scheduling belongs to server request context. A complete user request receives an immutable `receivedAt` timestamp before model execution, memory retrieval or job queueing. The generic agent loop retains that anchor across screenshot/external-input resumptions. GPT Live and external text sessions propagate the original server receipt into their specialist calls.

`save_scheduled_task` accepts exactly one of `delaySeconds` and `dueDate`. Positive delays resolve against request receipt. A passed deadline is rejected without moving it forward; the agent must obtain a new time. Absolute calendar dates retain explicit timezone offsets. Zero delay is the explicit immediate-dispatch exception: its due date is the save operation's current server time, and execution begins after persistence.

One-shot timed actions use `followUpActions` with strictly increasing `afterSeconds` offsets from the first scheduled phase. All phases inherit the resolved entity. Each phase is a normal ScheduledTask with one immediate Action effect and its own due date. A Cosmos transactional batch creates all rows in the same recurrence-family partition. There is no fallback that saves a start after its shutoff failed to persist. Explicit embedded waits are rejected instead of being mistaken for executable delays. Up to eight follow-up phases are supported; recurring timed sequences are rejected rather than silently reduced to incomplete actions.

`sequenceId`, `sequenceStep`, and `sequenceLength` identify the linked rows. Cancelling any remaining phase removes all remaining sequence rows in an atomic partition transaction. Changing a sequence's times or effects requires cancellation and recreation; moving one phase alone is rejected. Ordinary edits use an ETag-conditional replacement so they cannot overwrite a firing claim.

The server arms a timer for the next phase of each sequence. Timers refresh after persistence mutations and rebuild from durable rows on startup. The 30-second scan is reconciliation, not the firing clock. Actions in one sequence execute serially. If the backend resumes after several phases are overdue, earlier obsolete phases are skipped and audited before the latest due phase executes; a start is never replayed after its shutoff is already due.

Each dispatch is conditionally claimed using its Cosmos ETag before device execution. The claim includes a stable audit ID, owner PID and lease. Device execution is bounded to 60 seconds, within the 90-second dispatch lease. An interrupted claim is audited with unknown outcome and is never dispatched again. Immutable history creation tolerates a previously persisted audit ID during cleanup recovery. Recurring next-occurrence IDs are deterministic so a failed cleanup cannot create repeated future copies. This assumes the existing single-backend host deployment; claims do not provide a cross-host process-liveness service.

Timer precision does not eliminate model, network or physical-device latency. Offsets describe intended scheduled instants, not a promise of exact physical duration. Cancellation removes remaining dispatches and cannot undo an already dispatched effect. Background-job and downstream traces retain the evidence needed to distinguish acceptance, dispatch, API results and notification callbacks; none of those alone establishes audible playback.
